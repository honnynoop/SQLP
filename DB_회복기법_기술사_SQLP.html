01 · 개요 & 필요성
데이터베이스 회복(Recovery)이란?
정의 · 목적 · 필요성 · ACID와의 관계
기술사 SQLP
📖 정의 (Definition)
💡
데이터베이스 회복(Database Recovery)이란, 데이터베이스가 장애(Failure)로 인해 손상되거나 오류 상태가 되었을 때, 장애 발생 직전의 일관된 상태(Consistent State)로 복원(Restore)하는 일련의 과정 및 기법이다.
🎯 필요성 (Necessity)
⚡
데이터 무결성 보장
트랜잭션의 ACID 속성 중 원자성(Atomicity)과 지속성(Durability)을 보장하기 위해 필수적이다. 부분 완료된 트랜잭션의 결과를 제거하거나 완전히 반영해야 한다.
🛡️
시스템 신뢰성 확보
하드웨어 오류, 소프트웨어 버그, 운영자 실수 등 다양한 원인의 장애에도 데이터베이스 시스템이 지속적으로 운영될 수 있는 고가용성(High Availability)을 제공한다.
📋
법적·업무 요구 충족
금융, 의료, 공공 분야에서 데이터 손실 방지와 감사(Audit) 추적은 법적 의무사항이며, RPO(Recovery Point Objective)와 RTO(Recovery Time Objective)를 충족해야 한다.
🔁
트랜잭션 일관성 유지
다수의 트랜잭션이 동시에 실행되는 환경에서, 장애 발생 시 완료되지 않은 트랜잭션(미완료 트랜잭션)을 UNDO하고 완료된 트랜잭션을 REDO하여 일관성을 복원한다.
🔗 ACID와 회복의 관계
ACID 속성정의회복 기법과의 관계
원자성 (Atomicity)트랜잭션은 모두 실행되거나 전혀 실행되지 않아야 함미완료 트랜잭션 UNDO로 보장
일관성 (Consistency)트랜잭션 전후 DB는 항상 일관된 상태REDO + UNDO 조합으로 보장
격리성 (Isolation)트랜잭션은 서로 독립적으로 실행동시성 제어(Concurrency Control)가 담당
지속성 (Durability)완료된 트랜잭션의 결과는 영구적으로 저장로그(Log) 및 REDO로 보장
📊 회복 관련 핵심 용어
용어정의
RPO (Recovery Point Objective)데이터 손실을 허용할 수 있는 최대 시점 (얼마나 오래된 백업으로 복구 허용?)
RTO (Recovery Time Objective)장애 발생 후 허용 가능한 최대 복구 시간
REDO완료(Commit)된 트랜잭션의 변경을 재실행하여 영속성 보장
UNDO미완료(Uncommitted) 트랜잭션의 변경을 취소하여 원자성 보장
WAL (Write-Ahead Logging)데이터 변경 전 반드시 로그를 먼저 기록하는 원칙
로그(Log)트랜잭션의 모든 변경 내역을 순서대로 기록한 파일
체크포인트(Checkpoint)회복 시 로그 탐색을 줄이기 위해 주기적으로 저장하는 동기화 시점

02 · 장애 유형
데이터베이스 장애의 분류
트랜잭션 장애 · 시스템 장애 · 미디어 장애 · 통신 장애
⚠️ 장애 유형별 분류 및 특징
장애 유형발생 원인영향 범위복구 방법심각도
트랜잭션 장애
(Transaction Failure)		 논리적 오류, 교착상태(Deadlock), 사용자 취소, 제약 조건 위반 해당 트랜잭션만 해당 트랜잭션 UNDO 낮음
시스템 장애
(System Failure)		 전원 공급 중단, OS 충돌, DBMS 버그, 메모리 오류 메인 메모리(버퍼풀) 내용 소실. 디스크 데이터는 유지 로그 기반 REDO + UNDO 중간
미디어 장애
(Media/Disk Failure)		 디스크 헤드 충돌, 물리적 손상, 비트 부패(Bit Rot) 디스크 데이터 손상. 영구적 데이터 손실 가능 백업 + 아카이브 로그 적용 매우 높음
통신 장애
(Communication Failure)		 네트워크 단절, 분산 DB의 노드 간 통신 오류 분산 트랜잭션 일관성 문제 2PC(2-Phase Commit), Saga 패턴 중간

⚠️
교착상태(Deadlock)와 트랜잭션 장애: 교착상태는 두 트랜잭션이 서로의 잠금을 기다리며 무한 대기하는 상태다. DBMS는 교착상태 탐지 후 희생자(Victim)를 선택하여 강제 롤백(Rollback)한다. 이는 트랜잭션 장애의 일종이며, 해당 트랜잭션만 UNDO된다.

03 · 기본 원리
회복의 기본 원리 — REDO · UNDO · WAL
모든 회복 기법의 근간이 되는 3가지 핵심 원리
↪️ REDO (재실행)
대상: Commit된 트랜잭션 중 디스크에 반영되지 않은 것
목적: 지속성(Durability) 보장
방향: 로그를 처음부터 순방향으로 재적용
사용 데이터: After-Image (변경 후 값)
예시: 시스템 장애로 버퍼의 데이터가 디스크에 쓰이지 못한 경우
↩️ UNDO (취소)
대상: Commit되지 않은 미완료 트랜잭션
목적: 원자성(Atomicity) 보장
방향: 로그를 역방향으로 역순 취소
사용 데이터: Before-Image (변경 전 값)
예시: 트랜잭션 실행 중 오류 발생, 또는 시스템 장애 시 미완료 트랜잭션
📜 WAL (Write-Ahead Logging) 원칙
📜 WAL (Write-Ahead Logging) — 로그 선행 기록 원칙
모든 현대 DBMS 회복 기법의 근간. 데이터베이스를 실제로 변경하기 전에 반드시 로그 레코드를 먼저 안정적 저장소(디스크)에 기록해야 한다.
1️⃣
UNDO 규칙 (Steal Policy 지원): 트랜잭션이 데이터 항목을 변경하기 전에, 변경 전 값(Before-Image)을 로그에 먼저 기록해야 한다. → 이를 통해 트랜잭션 실패 시 UNDO 가능
2️⃣
REDO 규칙 (Force Policy 불필요): 트랜잭션을 Commit하기 전에, 해당 트랜잭션의 모든 로그 레코드(변경 후 값 포함)가 안정적 저장소에 기록되어야 한다. → 이를 통해 Commit 후 데이터 복구(REDO) 가능
🔧 버퍼 관리 정책과 회복의 관계
정책의미UNDO/REDO 필요 여부
Steal (훔치기 허용) 미완료(Uncommitted) 트랜잭션의 수정 내용을 디스크에 먼저 기록 가능 UNDO 필요
No-Steal (훔치기 금지) 미완료 트랜잭션의 수정 내용은 Commit 전에는 디스크에 기록 안 함 UNDO 불필요
Force (강제 기록) Commit 시 수정된 모든 페이지를 즉시 디스크에 기록 REDO 불필요
No-Force (강제 기록 안 함) Commit 시 수정 페이지를 즉시 디스크에 기록하지 않아도 됨 REDO 필요
Steal + No-Force (일반적) 대부분의 상용 DBMS가 채택 (성능 최우선) UNDO + REDO 모두 필요

05 · 로그 기반 회복 기법
Log-Based Recovery — 지연 갱신 · 즉시 갱신
가장 핵심적인 회복 기법 — 두 가지 갱신 방식 비교
기술사 필수 SQLP 출제
① 지연 갱신 기법 (Deferred Update / No-Undo, Redo)
💡
정의: 트랜잭션이 완료(Commit)되기 전까지 데이터베이스에 대한 실제 갱신을 지연시키는 기법. Commit 시점에 로그를 보고 일괄 적용한다. No-Steal + No-Force 정책 기반.
항목내용
별칭No-Undo/Redo 기법
핵심 원리트랜잭션 실행 중 변경 내용은 로그에만 기록. Commit 후 로그를 기반으로 실제 DB에 적용 (REDO만 수행)
로그 구성After-Image만 기록 (Before-Image 불필요)
장애 시 처리미완료 트랜잭션 → 로그 단순 버림 (UNDO 불필요). 완료 트랜잭션 → REDO 수행
장점UNDO 불필요로 회복 과정 단순, Before-Image 불필요
단점Commit 전까지 실제 DB에 미반영 → 대용량 트랜잭션 시 성능 저하. 버퍼 공간 과다 사용
적용 환경짧고 단순한 트랜잭션 위주 시스템, 교육용/소형 DBMS

② 즉시 갱신 기법 (Immediate Update / Undo, Redo)
💡
정의: 트랜잭션 실행 중 데이터 변경이 발생하면 즉시 데이터베이스에 반영하는 기법. 단, 로그를 먼저 기록(WAL 원칙)한 후 DB를 변경한다. Steal + No-Force 정책 기반.
항목내용
별칭Undo/Redo 기법 (부분 완료 시 Undo/No-Redo, 완전 완료 시 No-Undo/Redo로도 분류)
핵심 원리변경 즉시 DB에 반영. Before-Image와 After-Image를 모두 로그에 기록
로그 구성Before-Image + After-Image 모두 기록
장애 시 처리미완료 트랜잭션 → Before-Image로 UNDO. 완료 트랜잭션 → After-Image로 REDO
장점트랜잭션 중간에 DB 반영으로 버퍼 효율적 사용. 대용량 트랜잭션 처리 가능. 상용 DBMS 표준 방식
단점회복 시 UNDO + REDO 모두 수행해야 하여 회복 절차 복잡
적용 환경Oracle, SQL Server, PostgreSQL 등 모든 상용 DBMS

06 · 검사점 기법
Checkpoint — 회복 효율 극대화
로그 전체 탐색 없이 회복 범위를 축소하는 핵심 기법
기술사 단골 SQLP 출제
💡
검사점(Checkpoint)이란? 회복 시 로그 전체를 처음부터 탐색하면 시간이 매우 오래 걸린다. 이를 해결하기 위해 DBMS는 주기적으로 모든 버퍼의 더티 페이지를 디스크에 강제 기록하고, 그 시점을 기록한다. 회복 시 이 시점부터만 로그를 탐색하면 된다.
⚙️ 검사점 처리 과정
1
새 트랜잭션 시작 금지
검사점 생성 시작 시 새로운 트랜잭션의 시작을 일시적으로 금지한다 (일부 구현에서는 Fuzzy Checkpoint로 허용).
2
체크포인트 로그 레코드 기록
현재 활성 트랜잭션(Active Transaction List)과 더티 페이지 목록(Dirty Page List)을 담은 CHECKPOINT 로그 레코드를 기록한다.
3
더티 페이지 디스크 기록 (Flush)
버퍼 풀의 모든 수정된 페이지(Dirty Page)를 디스크에 강제로 기록한다. 이 시점 이후의 체크포인트 레코드는 REDO 대상에서 제외 가능.
4
체크포인트 완료 표시
END CHECKPOINT 로그 레코드를 기록하고, 체크포인트 LSN을 별도의 마스터 레코드(Master Record)에 저장한다.

🔄 Fuzzy Checkpoint (퍼지 검사점)
⚡
Fuzzy Checkpoint: 기본 체크포인트는 더티 페이지를 모두 디스크에 Flush할 때까지 새 트랜잭션을 막아 성능 저하가 심하다. Fuzzy Checkpoint는 체크포인트 시작과 종료 LSN을 모두 기록하고, 더티 페이지 기록을 백그라운드로 처리한다. 새 트랜잭션을 막지 않아 성능 저하 없이 체크포인트를 수행할 수 있다. ARIES 알고리즘이 채택하는 방식이며, Oracle의 Incremental Checkpoint도 유사한 개념이다.

08 · ARIES 알고리즘
ARIES — 현대 DBMS 회복의 표준
Algorithm for Recovery and Isolation Exploiting Semantics
기술사 심화 SQLP 심화
🏆
ARIES (Algorithm for Recovery and Isolation Exploiting Semantics): IBM 연구소에서 개발한 회복 알고리즘으로, Oracle, DB2, SQL Server, PostgreSQL 등 대부분의 현대 RDBMS가 채택하는 산업 표준 회복 기법이다. WAL + Steal + No-Force + Fuzzy Checkpoint를 결합한 최적 구현이다.
📋 ARIES의 3가지 핵심 원칙
📝
① WAL (Write-Ahead Logging)
데이터 변경 전 반드시 로그를 먼저 기록. UNDO와 REDO를 가능하게 하는 기본 전제. Before/After Image를 모두 로그에 기록한다.
🔁
② Repeating History
회복 시작 시 장애 발생 직전의 상태를 완전히 재현한다. 미완료 트랜잭션의 변경도 포함하여 모든 변경을 REDO한 후, 그 다음 UNDO를 수행한다.
📋
③ Logging Changes During UNDO
UNDO 작업 자체도 CLR(Compensation Log Record)로 로그에 기록한다. UNDO 중 다시 장애가 발생해도 이미 완료된 UNDO 작업을 반복하지 않아 효율적이다.
⚙️ ARIES 회복 3단계
1
분석 단계 (Analysis Phase)
마지막 체크포인트 LSN부터 로그 끝까지 순방향으로 탐색한다.
• ATT(Active Transaction Table): 장애 시점에 활성 상태였던 트랜잭션 목록 작성 → UNDO 대상
• DPT(Dirty Page Table): 디스크에 반영되지 않은 더티 페이지 목록 작성 → REDO 시작점 결정
• RedoLSN: DPT에서 가장 작은 RecLSN 값 → REDO 시작 위치 결정
2
REDO 단계 (Redo Phase)
분석 단계에서 구한 RedoLSN부터 로그 끝까지 순방향으로 탐색하며 모든 변경을 재적용한다.
• 미완료 트랜잭션의 변경도 포함하여 역사를 반복(Repeating History)
• 페이지의 PageLSN이 로그 레코드의 LSN보다 크거나 같으면 이미 반영된 것이므로 건너뜀
• CLR도 REDO 대상에 포함 (CLR은 절대 UNDO되지 않으므로)
3
UNDO 단계 (Undo Phase)
ATT에 있는 미완료 트랜잭션들을 역방향으로 탐색하여 변경을 취소한다.
• UNDO 수행 시마다 CLR(Compensation Log Record)을 기록하여 UNDO 작업을 로그화
• UNDO 도중 재장애 발생 시 CLR을 통해 이미 완료된 UNDO 재수행 방지
• 모든 활성 트랜잭션이 UNDO 완료되면 ABORT 로그 기록 후 완료

09 · 미디어 회복
Media Recovery — 디스크 장애 대응
백업 + 아카이브 로그를 이용한 완전·불완전 회복
기술사 SQLP DBA
💾
미디어 회복이란? 디스크 헤드 충돌, 물리적 손상 등으로 데이터 파일이 손상된 경우, 백업 파일과 아카이브 로그(Archive Log)를 이용하여 데이터베이스를 복구하는 기법이다. 시스템 회복(REDO/UNDO)으로는 해결할 수 없고, DBA가 수동으로 수행하는 외부 회복 작업이다.
📊 회복 유형 분류
회복 유형정의특징데이터 손실
완전 회복
(Complete Recovery)		 장애 발생 직전 시점까지 100% 데이터를 복구 백업 + 전체 아카이브 로그 + Online Redo Log 적용 없음
불완전 회복
(Incomplete Recovery)		 특정 시점(Point-in-Time)까지만 복구. 이후 데이터는 손실됨 일부 로그 손상, 특정 시점으로의 롤백 필요 시 발생
시점 회복 (PITR)
(Point-in-Time Recovery)		 특정 날짜·시간·SCN으로 복구 (불완전 회복의 일종) 실수로 삭제된 데이터 복구 등에 활용 부분 발생
⚙️ 미디어 회복 절차 (Oracle 예시)
1
장애 탐지 및 손상 파일 식별
경보(Alert Log)를 통해 손상된 데이터 파일을 파악. 해당 파일이 속한 테이블스페이스를 오프라인(Offline) 상태로 전환한다.
2
백업 파일 복원 (Restore)
가장 최근의 백업(Full Backup 또는 Incremental Backup)에서 손상된 파일을 복원한다. RMAN(Recovery Manager) 또는 OS 명령으로 수행.
3
아카이브 로그 적용 (Recover)
백업 시점부터 장애 직전까지의 아카이브 로그를 순서대로 적용(REDO)한다. 아카이브 로그는 온라인 리두 로그가 꽉 찼을 때 별도 저장된 로그다.
4
온라인 리두 로그 적용
아카이브 로그 적용 후, 현재 온라인 리두 로그(Online Redo Log)를 적용하여 장애 직전 상태까지 복구한다.
5
Open (데이터베이스 정상 오픈)
파일을 온라인 상태로 전환하고 DB를 정상 오픈한다. RESETLOGS 옵션으로 로그를 초기화할 수 있다 (불완전 회복 시 사용).

지연 갱신
(Deferred)		 Commit 후 DB 반영 불필요 필요 After-Image만 단순, Before-Image 불필요 버퍼 낭비, 성능 저하 거의 미사용
즉시 갱신
(Immediate)		 변경 즉시 DB 반영 필요 필요 Before+After 버퍼 효율, 범용 회복 절차 복잡 표준 방식

🎯 기술사 출제 핵심 포인트
① REDO vs UNDO 정확히 구분
• REDO: 완료(Commit)됐으나 디스크에 미반영 → After-Image 재적용
• UNDO: 미완료(Uncommit) 트랜잭션 → Before-Image로 취소
• 두 개념의 대상과 목적을 혼동하지 말 것
② WAL의 2가지 규칙
• UNDO 규칙: DB 변경 전 Before-Image 로그 기록
• REDO 규칙: Commit 전 After-Image 포함 모든 로그 기록
• WAL = UNDO 규칙 + REDO 규칙
③ 지연 vs 즉시 갱신 차이
• 지연: No-Steal, After-Image만, UNDO 불필요
• 즉시: Steal, Before+After, UNDO+REDO 모두 필요
• 상용 DBMS = 즉시 갱신 방식
④ ARIES 3단계 순서
1. 분석 (ATT, DPT 구성)
2. REDO (역사 반복, CLR도 REDO)
3. UNDO (CLR 기록하며 미완료 취소)
순서 오답 주의: 반드시 분석→REDO→UNDO
⑤ Checkpoint 역할

Oracle Redo LogOnline Redo Log → 가득 차면 Archive Log로 보관 (ARCHIVELOG 모드). Redo는 Commit 순서대로 기록. SCN(System Change Number)으로 순서 관리
Oracle Undo Segment이전 버전 데이터 보관. Read Consistency(문장 수준), Rollback, Flashback 기능 지원. UNDO_RETENTION 파라미터로 유지 시간 설정
Oracle CHECKPOINTDBWn 프로세스가 더티 버퍼를 디스크에 기록. LGWR이 Redo Log를 기록. Checkpoint 발생 시 SCN 정보를 Control File에 기록
Recovery 절차Instance Recovery (자동): SMON 프로세스가 재시작 시 자동 수행. Media Recovery (수동): DBA가 RMAN으로 수행
Flashback 기술Undo Segment의 Before-Image를 이용한 논리적 시점 복구. Flashback Table, Flashback Database, Flashback Query 등
