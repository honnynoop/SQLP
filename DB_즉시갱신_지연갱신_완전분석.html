01 · 개요 & 기본 원리
회복 기법의 배경과 WAL 원칙
왜 두 가지 방식이 존재하는가 — 버퍼 정책과 로그의 관계
📖 회복 기법이란?
💡
회복 기법(Recovery Technique)이란 트랜잭션 실행 중 장애가 발생하여 DB가 불일치 상태가 됐을 때, 장애 전 일관된 상태(Consistent State)로 복원하는 기법이다. 핵심은 언제 DB에 실제 변경을 반영하느냐에 따라 두 가지로 나뉜다.
📜 WAL (Write-Ahead Logging) — 모든 회복 기법의 전제
WAL 원칙 — 로그 선행 기록
⚙️ 버퍼 관리 정책 — 회복 기법 선택의 핵심
정책의미UNDO 필요?REDO 필요?적용 기법
Steal 미완료 트랜잭션의 변경을 Commit 전에도 디스크에 기록 가능 필요 — 즉시갱신
No-Steal 미완료 트랜잭션의 변경은 Commit 전까지 디스크에 기록 안 함 불필요 — 지연갱신
Force Commit 즉시 모든 변경 페이지를 디스크에 강제 기록 — 불필요 이론적 기법
No-Force Commit 시 디스크 기록 강제 안 함 (나중에 기록) — 필요 즉시갱신 / 지연갱신
Steal + No-Force 성능 최우선 정책 (상용 DBMS 표준) 필요 필요 즉시갱신 (표준)
No-Steal + No-Force 미완료 변경은 디스크 미기록, Commit도 즉시 강제 안 함 불필요 필요 지연갱신
⚡
02 · 즉시갱신 기법
Immediate Update — 변경 즉시 DB에 반영
Steal + No-Force 정책 | UNDO + REDO 모두 필요 | 상용 DBMS 표준 방식
산업 표준
💡
즉시갱신 기법(Immediate Update)이란 트랜잭션이 데이터를 변경할 때마다 즉시 DB 버퍼(메인 메모리)에 반영하고, 경우에 따라 디스크에도 선반영할 수 있는 기법이다. 단, WAL 원칙에 따라 반드시 로그를 먼저 기록(Before + After Image)한 후 DB를 변경한다. 장애 시 미완료 트랜잭션은 UNDO, 완료 트랜잭션은 REDO로 회복한다.
📊 즉시갱신 — 정상 실행 흐름 다이어그램
즉시갱신 기법 — 정상 트랜잭션 실행 과정
📋 즉시갱신 로그 레코드 구조
즉시갱신 — 로그 레코드 예시
LSN TID 유형 항목 Before Image (UNDO용) After Image (REDO용) 설명
LSN-001 T1 BEGIN — — — 트랜잭션 시작
LSN-002 T1 UPDATE salary 5000 ← UNDO 6000 ← REDO 데이터 변경 — Both Image 기록!
LSN-003 T1 COMMIT — — — 완료 — REDO 대상으로 분류
⭐ 즉시갱신의 핵심: Before Image(이전 값) + After Image(변경 후 값) 모두 기록 → Before로 UNDO, After로 REDO
📌 즉시갱신 상세 특징
항목내용
DB 갱신 시점변경 발생 즉시 DB 버퍼에 반영 (Commit 대기 없음)
버퍼 정책Steal (미완료 트랜잭션 변경도 디스크에 선기록 가능) + No-Force
로그 내용Before Image(변경 전 값) + After Image(변경 후 값) 모두 기록
UNDO 필요 여부필요 — 미완료 트랜잭션의 변경이 디스크에 반영될 수 있으므로
REDO 필요 여부필요 — Commit됐으나 버퍼에서 디스크로 미반영된 것을 재적용
메모리 사용효율적 (변경 즉시 반영하여 버퍼를 빨리 해제)
대용량 트랜잭션가능 (버퍼에 묶어두지 않으므로)
회복 복잡도복잡 (UNDO + REDO 모두 수행)
적용 DBMSOracle, SQL Server, MySQL InnoDB, PostgreSQL — 모든 상용 DBMS

03 · 지연갱신 기법
Deferred Update — Commit 후 DB에 반영
No-Steal + No-Force 정책 | REDO만 필요 | 단순하지만 성능 제약
💡
지연갱신 기법(Deferred Update)이란 트랜잭션이 실행되는 동안 모든 변경 내용을 로그에만 기록하고, 실제 DB에는 반영하지 않다가 트랜잭션이 성공적으로 완료(Commit)된 후 로그를 기반으로 DB에 일괄 반영하는 기법이다. 미완료 트랜잭션의 변경은 DB에 기록되지 않으므로 UNDO가 불필요하고, Commit 후 반영되지 않은 것을 REDO로 보완한다.
📊 지연갱신 — 정상 실행 흐름 다이어그램
지연갱신 기법 — 정상 트랜잭션 실행 과정
📋 지연갱신 로그 레코드 구조
📝
지연갱신에서는 After Image(변경 후 값)만 기록한다. 미완료 트랜잭션의 변경은 DB에 반영되지 않으므로 Before Image가 필요 없다. UNDO 자체가 불필요하기 때문이다.
지연갱신 — 로그 레코드 예시 (After Image만 존재)
LSN TID 유형 항목 Before Image After Image (REDO용)
LSN-001 T1 BEGIN — 기록 안 함 —
LSN-002 T1 UPDATE salary — (불필요) 6000 ← REDO용
LSN-003 T1 COMMIT — — —
⭐ 지연갱신의 핵심: After Image만 기록 (Before Image 불필요) → UNDO 없이 Commit 후 REDO로만 DB 반영
📌 지연갱신 상세 특징
항목내용
DB 갱신 시점Commit 완료 후에만 DB에 반영 (실행 중에는 로그에만 기록)
버퍼 정책No-Steal (미완료 트랜잭션 변경은 디스크에 절대 선기록 안 함)
로그 내용After Image(변경 후 값)만 기록 — Before Image 불필요
UNDO 필요 여부불필요 — 미완료 트랜잭션의 변경이 DB에 없으므로 취소할 것도 없음
REDO 필요 여부필요 — Commit됐으나 DB 미반영 시 After Image로 재적용
메모리 사용많음 (Commit 전까지 모든 변경을 버퍼에 보관해야 함)
대용량 트랜잭션불리 (버퍼를 Commit까지 점유, 버퍼 부족 시 문제 발생)
회복 복잡도단순 (REDO만 수행, 로그 탐색도 간단)
적용 DBMS거의 미사용 (이론/교육용). 일부 경량 DB에서 활용

04 · 장애 시나리오 분석
각 기법에서 장애 발생 시 데이터 상태
어떤 데이터가 손상되고 무엇을 복구해야 하는가
⚡ 즉시갱신 — 장애 발생 시나리오 4가지
즉시갱신 — 장애 발생 위치에 따른 시나리오
시나리오로그 상태디스크 상태필요한 회복이유
T1
체크포인트 전 완료		 COMMIT 있음 디스크 반영 확실 회복 불필요 체크포인트 시 이미 디스크에 Flush됨
T2
체크포인트 후 Commit		 COMMIT 있음 버퍼에만 있고 디스크 미반영 가능 REDO 필요 ↪️ Commit은 됐으나 장애로 디스크에 기록 못했을 수 있음
T3
체크포인트 전 시작, 미완료		 COMMIT 없음 변경이 일부 디스크에 반영될 수 있음(Steal) UNDO 필요 ↩️ 미완료 변경이 디스크에 기록됐을 수 있으므로 취소
T4
체크포인트 후 시작, 미완료		 COMMIT 없음 변경이 일부 디스크 반영 가능(Steal) UNDO 필요 ↩️ 동일. 미완료 트랜잭션은 반드시 롤백
⏳ 지연갱신 — 장애 발생 시나리오
지연갱신 — 장애 발생 위치에 따른 시나리오
시나리오로그 상태디스크 상태필요한 회복이유
T1
Commit + DB 반영 완료		 COMMIT 있음 이미 반영됨 회복 불필요 모든 것이 정상 완료됨
T2
Commit 완료, DB 미반영		 COMMIT 있음 로그만 있고 DB 미반영 REDO 필요 ↪️ Commit 후 DB 반영 도중 장애. After Image로 REDO
T3
미완료 트랜잭션		 COMMIT 없음 DB에 아무 변경 없음 UNDO 불필요
(로그 버림)		 No-Steal 정책으로 DB에 전혀 기록 안 됨

05 · 해결 방법 & 과정
장애 발생 후 단계별 회복 수행 과정
UNDO 과정 · REDO 과정 · 시스템 재시작 후 회복 절차
🔧 즉시갱신 — 장애 회복 전체 과정
즉시갱신 회복 절차 — 시스템 재시작 후
1
로그 분석 — REDO/UNDO 대상 분류
시스템 재시작 후 체크포인트부터 로그를 순방향으로 탐색한다.
• REDO 리스트: COMMIT 로그가 있는 트랜잭션 목록 작성
• UNDO 리스트: COMMIT 로그가 없는 트랜잭션 목록 작성
2
REDO 수행 — Commit 완료 트랜잭션 재적용
로그를 순방향(앞→뒤)으로 탐색하며 REDO 리스트의 트랜잭션에 대해 After Image를 DB에 재적용한다.
• 이미 디스크에 반영된 것도 있을 수 있지만 안전하게 모두 재적용 (멱등성 보장)
• PageLSN 비교로 이미 적용된 것은 건너뜀 (ARIES 방식)
3
UNDO 수행 — 미완료 트랜잭션 취소
로그를 역방향(뒤→앞)으로 탐색하며 UNDO 리스트의 트랜잭션에 대해 Before Image로 DB를 원상복구한다.
• 역순으로 수행해야 데이터 일관성 보장
• UNDO 작업도 CLR(보상 로그)로 기록하여 UNDO 중 재장애 대비
4
회복 완료 — 정상 운영 재개
REDO + UNDO 완료 후 DB가 일관된 상태로 복원된다. DBMS는 정상 운영 모드로 전환하고 신규 트랜잭션을 받기 시작한다.
🌿 지연갱신 — 장애 회복 과정
지연갱신 회복 — 단순한 REDO만 수행
1
로그 분석 — COMMIT 있는 트랜잭션만 선별
로그를 순방향으로 탐색하여 COMMIT 레코드가 있는 트랜잭션만 REDO 리스트에 포함한다. COMMIT 없는 트랜잭션은 DB에 영향이 없으므로 그냥 무시한다.
2
REDO 수행 — After Image로 DB 반영
COMMIT이 있는 트랜잭션의 로그를 순방향으로 재적용하여 DB에 반영한다. Before Image가 없으므로 UNDO 과정 자체가 없다.
3
회복 완료 — 정상 운영 재개
UNDO 없이 REDO만으로 회복이 완료된다. 회복 절차가 즉시갱신에 비해 훨씬 단순하다.

07 · 효과적인 회복 방법 제시
현대 DBMS의 최적 회복 전략
즉시갱신 + 검사점 + ARIES 조합 — 성능과 안정성의 최적 균형
🏆
단일 기법만으로는 최적의 회복을 달성하기 어렵다. 현대 상용 DBMS는 즉시갱신 + Fuzzy Checkpoint + ARIES 알고리즘을 조합하여 성능과 신뢰성을 동시에 달성한다.
✅ 효과적인 회복을 위한 5가지 핵심 전략
⚡
전략 1. 즉시갱신 + WAL 원칙 철저 준수
Steal + No-Force 정책으로 버퍼 효율성 극대화. 모든 변경 전 반드시 Before/After Image를 로그에 먼저 기록(WAL). 대용량 트랜잭션도 버퍼 부족 없이 처리 가능.
→ 성능과 회복 가능성 동시 확보
🏁
전략 2. Fuzzy Checkpoint 주기적 수행
Sharp Checkpoint는 전체 버퍼 Flush 동안 새 트랜잭션을 막아 성능 저하. Fuzzy Checkpoint는 시작/종료 LSN을 기록하고 백그라운드로 처리하여 운영 중단 없이 체크포인트 수행.
→ 회복 범위 축소 + 운영 성능 유지
🧮
전략 3. ARIES 알고리즘 적용
분석(Analysis) → REDO → UNDO 3단계로 최소 범위만 처리. CLR(보상 로그)로 UNDO 중 재장애 시에도 안전. DPT(더티 페이지 테이블)로 REDO 최소 범위 결정.
→ 회복 시간 최소화 + 안전성 보장
💾
전략 4. 아카이브 로그 + 정기 백업
로그 기반 회복(REDO/UNDO)은 시스템 고장에만 대응 가능. 기억장치 장애에 대비하여 정기적인 Full/Incremental 백업과 ARCHIVELOG 모드 활성화 필수.
→ 디스크 장애도 완전 회복 가능
🛡️
전략 5. 이중화 + 고가용성 구성
단일 회복 기법의 한계 — 회복 시간(RTO) 동안 서비스 중단. RAC(Real Application Cluster), Data Guard, Standby DB 구성으로 장애 시 즉각 페일오버.
→ RTO ≈ 0 달성 (무중단 운영)
🔍
전략 6. 사용자 장애 대비 — Flashback
로그/UNDO 기반 회복은 시스템 장애만 대상. 사용자 실수(잘못된 DELETE 등)는 Flashback Query/Table로 Undo Segment의 Before Image를 이용하여 특정 시점으로 빠르게 복원.
→ 사용자 장애도 신속 회복

장애 유형발생 상황최적 회복 방법핵심 기법회복 시간
트랜잭션 장애 교착상태, 무결성 위반 해당 트랜잭션만 UNDO (즉시갱신) Before Image 역방향 적용 수 초 이내

🏆 현대 DBMS 회복 기법 결론
🎯
결론: 현대 상용 DBMS에서 가장 효과적인 회복 방법은
① 즉시갱신 기법 (Steal + No-Force) — 성능과 회복 가능성 확보
② WAL 원칙 (Before + After Image 기록) — UNDO + REDO 보장
③ Fuzzy Checkpoint — 회복 범위 축소, 운영 성능 유지
④ ARIES 알고리즘 — 최소 범위로 빠른 회복, UNDO 중 재장애 대비
⑤ 아카이브 로그 + 정기 백업 — 기억장치 장애 대응
⑥ Flashback / PITR — 사용자 장애 신속 대응

지연갱신 기법은 회복이 단순하나 버퍼 낭비와 대용량 트랜잭션 처리 한계로 상용 환경에서는 즉시갱신 기법이 압도적으로 우세하다.
